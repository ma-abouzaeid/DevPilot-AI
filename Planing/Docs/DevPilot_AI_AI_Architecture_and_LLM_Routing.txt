============================================================
1. PURPOSE
============================================================

This document defines the AI architecture for DevPilot AI.

The AI layer is responsible for:

- Developer problem debugging.
- Root-cause explanation.
- Step-by-step solutions.
- Solution adaptation.
- Educational article generation.
- Article improvement.
- Challenge generation.
- Challenge evaluation.
- GitHub repository analysis.
- AI code review.
- Solution synthesis.
- Telegram AI fallback.

The system must not depend on one LLM provider.

Instead, DevPilot AI uses an internal AI Gateway that can route requests across
multiple free/free-tier providers and models.

3. IMPORTANT DESIGN DECISION
============================================================

The application must never call a provider directly from business services.

Incorrect:

ProblemService
    -> Gemini API

Correct:

ProblemService
    -> AI Gateway
        -> Provider Router
            -> Selected Provider

This prevents the application from becoming dependent on any one provider.

============================================================
4. PROVIDER TYPES
============================================================

The AI Gateway should support two provider categories.

4.1 Direct Providers

The application communicates directly with the provider API.

Examples to evaluate:
- Google Gemini API
- Groq
- GitHub Models
- Cerebras
- Mistral
- NVIDIA NIM
- Cloudflare Workers AI
- Hugging Face Inference Providers

4.2 Aggregator / Unified Providers

One API may expose multiple models.

Examples:
- OpenRouter
- CodeCraft API

The architecture should treat both categories as AI providers.

============================================================
7. GOOGLE GEMINI
============================================================

Google Gemini should be included as a major provider.

Current Google documentation provides a free developer tier with free input and
output tokens for eligible models and access through Google AI Studio.

The current pricing page also lists multiple Flash-family models with
free-of-charge standard input/output pricing.

Gemini should be considered for:
- Debugging.
- Root-cause analysis.
- Article generation.
- Code review.
- Repository analysis when the context is within model limits.

Important privacy consideration:
Google's current pricing documentation states that content in the free tier is
used to improve Google's products.

Therefore:

- Do not silently send sensitive/private code to the free Gemini tier.
- Provider privacy policy must be part of provider configuration.
- Private-code routing must be controlled by policy.

============================================================
8. GROQ
============================================================

Groq is a strong candidate for fast coding/debugging requests.

Current Groq documentation exposes rate-limit dimensions such as:
- RPM
- RPD
- TPM
- TPD

Groq also returns rate-limit headers that can be used by the AI Gateway to
understand remaining request/token capacity and reset timing.

Therefore the AI Gateway should prefer runtime quota headers over hard-coded
numbers.

Suitable use cases:
- Short debugging.
- Fast explanations.
- Code review.
- Interactive developer conversations.

============================================================
9. OPENROUTER
============================================================

OpenRouter should be treated as a provider/aggregator.

Its free-model collection currently contains multiple $0 models, and the
OpenRouter free-model router can select from available free models.

Advantages:
- Many models behind one API.
- Useful fallback when a direct provider is unavailable.
- OpenAI-compatible API shape.

Important:
- OpenRouter free models do not all have identical privacy/retention terms.
- The provider/model metadata must store privacy and usage policies.
- A free model may disappear or move away from the free tier.

============================================================
10. CODECRAFT API
============================================================

CodeCraft API provides an OpenAI-compatible endpoint.

Its current site advertises:
- Free monthly token allowance.
- Multiple models.
- Streaming.
- Tool calling.
- Vision input for capable models.
- Usage analytics.

For DevPilot AI it can be used as:
- A fallback provider.
- A specialized provider for model capabilities.
- A compatibility-friendly provider because of its OpenAI-style API.

The free tier should be treated as limited quota, not unlimited free usage.

============================================================
12. AI REQUEST ROUTING
============================================================

Every AI request follows this process:

1. Receive request.
2. Validate request.
3. Identify operation type.
4. Identify sensitivity level.
5. Search reusable knowledge.
6. Determine whether fresh AI generation is required.
7. Select eligible providers/models.
8. Rank providers/models.
9. Send request.
10. Validate response.
11. Store request/response metadata.
12. Return normalized response.

============================================================
13. PROVIDER SELECTION RULES
============================================================

Provider selection should consider:

1. Provider active status.
2. Model active status.
3. Current availability.
4. Rate-limit/usage availability.
5. Required capabilities.
6. Data/privacy policy.
7. Task type.
8. Context size.
9. Provider priority.
10. Recent failure rate.

Example:

Debugging + image screenshot
    ->
Requires Vision
    ->
Filter non-vision models
    ->
Filter unavailable models
    ->
Filter providers that do not allow the request's privacy level
    ->
Rank remaining models
    ->
Send request

============================================================
16. SIMILARITY + SOLUTION REUSE
============================================================

For every new problem:

Search:
- Problem description
- Error message
- Stack trace
- Technology
- Framework
- Relevant code
- Existing embeddings

If a sufficiently similar problem is found:

1. Retrieve the most successful solution.
2. Retrieve supporting article knowledge.
3. Send only relevant context to the LLM.
4. Ask the LLM to adapt and validate the old solution.
5. Return the adapted result.
6. Store the new request and the successful result.

Do not blindly return historical answers.

============================================================
17. SOLUTION SYNTHESIS
============================================================

If multiple successful solution variants exist:

Solution A -> Success
Solution B -> Success
Solution C -> Success

The system may send the evidence to the AI Gateway.

The AI produces:

Improved Solution
      |
      v
New Knowledge Article Version

The previous versions remain stored.

============================================================
19. RESPONSE VALIDATION
============================================================

The API should not trust raw LLM output.

Validate:
- Required fields.
- JSON structure.
- Maximum sizes.
- Allowed enum values.
- Safe content formatting.
- Unexpected output.
- Provider-specific response format.

If response is invalid:
1. Try response normalization.
2. Retry the same provider if appropriate.
3. Otherwise fail over.
4. Record the failure.

============================================================
20. RETRY / FAILOVER POLICY
============================================================

Failure categories:

A. Rate limit
Action:
- Read provider reset information when available.
- Put provider/model into cooldown.
- Select next eligible provider.

B. Temporary network/service error
Action:
- Retry with bounded backoff.
- Then fail over.

C. Invalid provider response
Action:
- Attempt normalization.
- If unsuccessful, fail over.

D. Authentication/configuration error
Action:
- Disable provider/model.
- Alert administrator.
- Do not repeatedly retry.

E. Content policy rejection
Action:
- Do not blindly retry the same request across providers.
- Return a safe result or request appropriate user changes.

============================================================
21. DO NOT RANDOMLY ROTATE PROVIDERS
============================================================

Provider switching must not be random.

Recommended priority model:

Score =
    ProviderPriority
    + CapabilityMatch
    + AvailabilityScore
    + QuotaScore
    + ReliabilityScore
    + PrivacyCompatibility

The provider with the best eligible score receives the request.

Randomization may be used only when two providers are intentionally tied.

============================================================
22. PROVIDER COOLDOWN
============================================================

When a provider reaches a rate limit:

Provider A
    ->
CooldownUntil = reset time

The provider router excludes it until:
- Reset time passes, or
- Administrator manually re-enables it.

This prevents repeated failures.

============================================================
26. PRIVATE CODE / DATA PROTECTION
============================================================

AI requests may contain private repository content.

Therefore the platform should classify requests:

PUBLIC
INTERNAL
PRIVATE
SENSITIVE

Provider eligibility should depend on policy.

Example:

Private Repository
    ->
Provider.AllowsPrivateCode = true
    ->
Provider allowed

Private Repository
    ->
Provider.AllowsPrivateCode = false
    ->
Provider rejected

The application must never assume that every free LLM provider has the same
privacy policy.

============================================================
28. IMAGE / SCREENSHOT DEBUGGING
============================================================

When the developer uploads a screenshot:

1. Detect whether the selected model supports vision.
2. Filter providers/models.
3. Compress/normalize image when appropriate.
4. Send image plus only necessary technical context.
5. Store metadata.
6. Return structured debugging response.

Do not send screenshots to text-only models.

============================================================
35. FREE-TIER SAFETY RULE
============================================================

"Free" must never be interpreted as:
- Unlimited.
- Permanently available.
- Identical across providers.
- Safe for every type of data.
- Guaranteed to remain free.

The provider catalog and limits must be configurable.

============================================================
40. FINAL DESIGN GOAL
============================================================

The AI layer must be:

- Provider-independent.
- Free-tier aware.
- Token-efficient.
- Privacy-aware.
- Fault tolerant.
- Configurable.
- Observable.
- Reusable across all DevPilot AI modules.

The key architecture principle is:

"Search existing proven knowledge first, use the smallest appropriate AI
context second, and use the best available eligible free model through one
central AI Gateway."
