2. ARCHITECTURAL PRINCIPLES
================================================================================================

2.1 Developer-Centered

The User is the primary owner of personal application activity.

A User can own or initiate:
- Problems
- Challenge Attempts
- GitHub Accounts
- Code Reviews
- AI Requests
- Subscriptions
- Usage records

2.2 Problem-Centered

Problem is the central business object for debugging.

A Problem can connect to:
- Problem Requests
- Attachments
- Debugging Attempts
- Feedback
- Successful Solutions
- Knowledge Articles
- Technologies
- Challenges
- AI Requests
- Similarity Matches

2.3 History Preservation

DevPilot AI intentionally preserves:
- Previous debugging attempts
- Successful solutions
- Article versions
- Challenge attempts
- Evaluations
- AI usage information
- Audit history

2.4 Knowledge Reuse

Solved problems become reusable knowledge.

Similar future problems can reuse:
- Successful Solutions
- Knowledge Articles
- Similarity Matches
- Relevant debugging history

2.5 AI Provider Independence

Application business modules do not depend directly on one LLM provider.

The AI Gateway selects:
- Provider
- Model
- Priority
- Availability
- Fallback provider/model

Usage accounting remains independent from provider selection.

2.6 Separation of Rate Limits and Quotas

RATE LIMIT:
Controls request frequency over short windows.

Examples:
- 5 AI requests per minute
- 10 follow-up requests per minute
- 5 login attempts per 5 minutes

USAGE QUOTA:
Controls cumulative consumption over a usage period.

Examples:
- 50 AI credits per month
- Maximum analyses in a period
- Feature-specific allowances

Rate limiting is NOT the usage accounting system.

2.7 No Cascade Delete

This project has a strict NO CASCADE policy.

Database foreign keys must not use:
    ON DELETE CASCADE

EF Core relationships must use a non-cascading behavior, with
DeleteBehavior.NoAction preferred where appropriate.

Soft Delete is implemented at the application/data-query level and must not
be implemented using database cascade deletion.

2.8 Soft Delete Is Selective

Soft Delete is NOT applied to every table.

It is used only when the entity has meaningful "deleted" semantics and the
row should remain in the database.

Entities with their own lifecycle (for example RefreshToken, AIModel,
EmailVerification, UserSubscription) must use their dedicated state model
instead of an unnecessary IsDeleted flag.

5. COMMON TIMESTAMP AND SOFT DELETE CONVENTIONS
================================================================================================

Common timestamp fields where applicable:

CreatedAt
    Date/time the row was created.

UpdatedAt
    Date/time the row was last updated.

DeletedAt
    Date/time the row was logically deleted.

Soft-deletable entities use:

IsDeleted BIT NOT NULL DEFAULT 0
DeletedAt DATETIME2 NULL

Existing records after migration:
IsDeleted = 0
DeletedAt = NULL

Global Query Filter behavior:
Normal queries automatically exclude IsDeleted = true.

Deleted data may only be queried intentionally using an internal/admin
mechanism such as IgnoreQueryFilters(), subject to authorization.

IMPORTANT:
IsDeleted is NOT automatically added to:
- RefreshTokens
- EmailVerifications
- AuditLogs
- AIUsageEvents
- UsageLedger
- Roles
- entities whose lifecycle is better represented by an existing state field.

6. TABLE 01 - Users
================================================================================================

Purpose:
Stores developer accounts.

Main fields:
- UserId INT PK
- Name NVARCHAR(150)
- Email NVARCHAR(255) UNIQUE
- PasswordHash NVARCHAR(500)
- EmailVerifiedAt DATETIME2 NULL
- CreatedAt DATETIME2
- IsDeleted BIT NOT NULL DEFAULT 0
- DeletedAt DATETIME2 NULL

Relationships:
- Users 1:N UserRoles
- Users 1:N EmailVerifications
- Users 1:N RefreshTokens
- Users 1:N Problems
- Users 1:N ChallengeAttempts
- Users 1:N GitHubAccounts
- Users 1:N CodeReviews
- Users 1:N AIRequests
- Users 1:N UserSubscriptions
- Users 1:N AIUsageEvents
- Users 1:N UsagePeriods
- Users 1:N UsageLedger entries
- Users 1:N AuditLogs

Soft Delete:
YES.

Delete behavior:
- IsDeleted = true
- DeletedAt = UTC timestamp
- Active refresh tokens are revoked
- Existing history remains
- Login is blocked
- Refresh is blocked
- Protected APIs reject deleted users
- Password reset is blocked
- Email verification workflows are blocked

Email uniqueness:
The existing unique Users.Email rule should remain unless a future explicit
product decision changes identity recycling behavior.

Account deletion is NOT a physical row deletion.

9. TABLE 04 - EmailVerifications
================================================================================================

Purpose:
Stores email verification workflows.

Main fields:
- VerificationId INT PK
- UserId INT FK
- CodeHash NVARCHAR(500)
- TokenHash NVARCHAR(500) NULL
- Method VARCHAR(20)
- ExpiresAt DATETIME2
- Attempts INT
- VerifiedAt DATETIME2 NULL
- CreatedAt DATETIME2

Relationships:
- Users 1:N EmailVerifications

Soft Delete:
NO.

Lifecycle:
EmailVerifications have a verification-specific state:
- Pending
- Verified
- Expired
- Invalidated by a newer verification

Security:
- Store hashes, not raw OTP/token values.
- Apply expiration.
- Apply maximum attempts.
- Apply resend cooldown.
- Deleted accounts cannot verify or resend verification.

Historical verification rows may remain for security and audit purposes.

44. AI QUOTA AND CREDIT RULES
================================================================================================

AI Usage Quota controls cumulative consumption.

A request must pass all of the following:

1. Authentication
2. Authorization
3. Rate limit
4. Input validation
5. Plan feature access
6. Available quota/credits
7. Concurrency protection

Reservation:
Before expensive AI execution:

    Reserve credits

Provider call:
    Execute AI request

Finalization:
    Capture actual tokens
    Capture actual/estimated cost
    Charge actual usage
    Release unused reservation

Example:

    Reserved = 5 credits
    Actual = 3 credits

    Charge = 3
    Release = 2

Failure:
If the provider definitely did not process the request:
    Release reservation

Ambiguous timeout:
If the provider may have processed the request:
    Do NOT automatically refund and retry blindly.
    Reconcile according to provider behavior and idempotency strategy.

    Logical AI Operations: 1
    Provider Calls:         2

This gives the admin dashboard accurate provider-level accounting.

50. RATE LIMIT PARTITIONING
================================================================================================

Authenticated endpoints:
    Partition by trusted UserId.

Anonymous endpoints:
    Partition by validated client/IP identity where appropriate.

Do not trust arbitrary client-provided headers as partition keys.

If deployed behind a reverse proxy:
Configure trusted forwarded headers correctly.

Do not blindly trust X-Forwarded-For from untrusted sources.

Authentication endpoints require both:
- client/IP protection
- account-level protections where appropriate

This prevents attackers from evading limits by switching target accounts.


================================================================================================
51. RATE LIMIT RESPONSE
================================================================================================

Exceeded limit:

    HTTP 429 Too Many Requests

Standard error envelope:

    {
      "success": false,
      "errorCode": "RATE_LIMIT_EXCEEDED",
      "message": "Too many requests. Please try again later.",
      "requestId": "..."
    }

Where supported:
    Retry-After: <seconds>

Rate-limited requests MUST be rejected before invoking the LLM provider.

Rate-limit configuration details must not be exposed unnecessarily.


================================================================================================
52. RATE LIMIT VS AI QUOTA
================================================================================================

Example:

User Plan:
    50 AI Credits / period

Rate Limit:
    5 AI analysis requests / minute

Scenario A:
    User makes 5 requests in one minute.
    Rate limit allows them.
    Quota is still reduced according to actual usage.

Scenario B:
    User has 0 credits remaining.
    Rate limit allows the request.
    Quota service rejects it BEFORE provider invocation.

Scenario C:
    User sends 20 requests in one second.
    Rate limiter rejects excess requests with 429.
    Those rejected requests consume no AI credits.

Therefore:

    Rate Limit = request frequency protection
    Quota       = cumulative consumption protection

54. CONCURRENCY CONTROL
================================================================================================

AI credit accounting must be concurrency-safe.

Example:

    User balance = 10 credits

    Request A wants 8
    Request B wants 8

Incorrect:
    A reads 10
    B reads 10
    A spends 8
    B spends 8

Correct:
    A reserves 8
    remaining = 2

    B attempts to reserve 8
    B is rejected

Reservation and accounting must use database-safe transactions/locking or an
equivalent concurrency-safe mechanism.

Do not rely on an in-memory variable as the durable credit balance.

- Administrative credit adjustments

- UsagePeriodId
- AIUsageEventId
- ReferenceId / idempotency reference

Plans:
- Code UNIQUE
- IsDefault / Status combinations as required by SQL Server constraints

Features:
- Key UNIQUE


================================================================================================
72. DATA INTEGRITY RULES
================================================================================================

Never trust the frontend for:

- PlanId
- IsAdmin
- Credit balance
- Token counts
- Cost
- Subscription status
- Usage values
- Rate-limit partition identity

All important values must be determined server-side.

Never allow a normal Developer endpoint to mutate:
- AIUsageEvents
- UsageLedger
- AuditLogs
- Plan definitions
- UserSubscriptions outside allowed user-facing operations


================================================================================================
73. SECURITY RULES
================================================================================================

The database must never contain plaintext secrets.

Never store:
- Brevo API keys
- LLM provider keys
- GitHub access tokens in plaintext
- Passwords
- raw refresh tokens
- raw OTP codes
- reset tokens

Store:
- hashes
- encrypted credentials where required
- secure references
- safe metadata

Audit and usage records must not accidentally capture sensitive secrets from
prompts, headers, or exceptions.


================================================================================================
74. ERROR AND FAILURE ACCOUNTING
================================================================================================

AI operation statuses should distinguish:

- Pending
- Success
- Failed
- RateLimited
- Cancelled

Provider-level usage event may additionally track:
- Provider timeout
- Provider rejection
- Validation failure
- Fallback success
- Unknown/ambiguous outcome

Quota behavior:

REJECTED BEFORE AI:
    No AI usage charge.

PROVIDER DEFINITELY NOT CALLED:
    Reservation can be released.

PROVIDER CALLED AND FAILED:
    Preserve the usage event and follow the configured accounting policy.

TIMEOUT WITH UNKNOWN PROVIDER OUTCOME:
    Do not blindly refund and retry.


================================================================================================
75. ADMIN PLAN CHANGE AUDITING
================================================================================================

Every important plan operation should create an AuditLog.

Example:

    Action:
        PLAN_LIMIT_UPDATED

    Entity:
        Plan

    EntityId:
        2

    OldValues:
        CreditsPerPeriod = 50

    NewValues:
        CreditsPerPeriod = 100

    Actor:
        Administrator UserId

    CreatedAt:
        UTC timestamp

This gives administrators accountability without storing secrets.

82. DO NOT CONFUSE THESE CONCEPTS
================================================================================================

Soft Delete:
    "This business object is no longer active/visible."

Archive:
    "This configuration/content is retired but remains a valid historical
    record."

Revoke:
    "This credential/session is no longer valid."

IsActive:
    "This configuration/provider is currently enabled."

IsAvailable:
    "This model/service is currently usable."

IsUsed:
    "This refresh token has already been consumed."

Quota:
    "How much cumulative AI consumption is allowed."

Rate Limit:
    "How frequently requests may arrive."

AIRequest:
    "One logical AI operation."

AIUsageEvent:
    "One actual provider/model execution."

85. FINAL ARCHITECTURAL DECISION
================================================================================================

The updated DevPilot AI architecture is intentionally divided into:

CORE PRODUCT DATA
    Users
    Problems
    Knowledge
    Challenges
    GitHub
    Code Review

AUTHENTICATION / SECURITY
    Roles
    UserRoles
    EmailVerifications
    RefreshTokens
    AuditLogs

COMMERCIAL / ENTITLEMENT FOUNDATION
    Plans
    Features
    PlanFeatures
    UserSubscriptions

AI ACCOUNTING
    AIProviders
    AIModels
    AIRequests
    AIUsageEvents
    UsagePeriods
    UsageLedger

SEARCH / OPTIMIZATION
    ProblemEmbeddings
    SimilarityMatches
    ProblemSolutions

PROTECTION
    Native Rate Limiting
    AI Concurrency Limits

SOFT DELETE
    Only meaningful business entities receive:
        IsDeleted
        DeletedAt

NO CASCADE
    All foreign keys remain non-cascading.

The database therefore becomes capable of answering:

"Who used the system?"
"What plan are they on?"
"What features are enabled?"
"How many logical AI requests were made?"
"How many provider calls actually happened?"
"Which provider/model handled them?"
"How many input tokens were used?"
"How many output tokens were used?"
"How many total tokens were consumed?"
"What was the estimated/actual cost?"
"How many credits were reserved?"
"How many credits were charged?"
"How many credits were refunded?"
"How much of the user's period quota remains?"
"Which requests were rejected by rate limiting?"
"Which requests failed?"
"What changed administratively?"
"What was soft-deleted?"
"Can historical knowledge still be preserved?"

This is the intended data foundation for future Plan Management, AI Usage,
Credits, Quotas, Rate Limiting, and Administrative Monitoring without
redesigning the core DevPilot AI database.

   lifecycle model.
