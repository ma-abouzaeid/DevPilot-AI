DEV-PILOT AI
DATABASE DOCUMENTATION
============================================================

Document Version: 1.0
Project: DevPilot AI
Database: SQL Server
Database Scope: Core ERD
Current Core Tables: 26
Primary Purpose:
Support the complete DevPilot AI workflow:

Developer
    -> Problem
    -> Requests / Debugging Attempts
    -> Successful Solution
    -> Knowledge Article
    -> Practice Challenge
    -> GitHub Repository
    -> AI Evaluation / Code Review

The database also supports:
- Similar problem search
- Reuse of successful solutions
- LLM token/usage tracking
- Multiple AI providers and models
- GitHub integration
- Telegram knowledge lookup
- Continuous knowledge/article improvement

IMPORTANT:
This document describes the current Core ERD. Supporting tables such as
Notifications, DiscordEvents, and AuditLogs are intentionally excluded from
the current Core ERD to keep the main database model focused and understandable.

============================================================
1. DATABASE DESIGN PRINCIPLES
============================================================

1.1 Developer-Centered
The main business entity is the Developer (User).

1.2 Problem-Centered
A Problem is the central business object connecting debugging, solutions,
knowledge articles, challenges, AI processing, and statistics.

1.3 Full Debugging History
The database keeps the requests, attempts, and developer feedback instead of
storing only the final answer.

1.4 Knowledge Reuse
Successful solutions are stored so similar future problems can reuse them.

1.5 Knowledge Evolution
A problem can have multiple successful solutions and an article can have
multiple versions.

1.6 GitHub Integration
GitHub accounts, repositories, challenges, and code reviews are stored and
linked to developers.

1.7 AI Provider Independence
AI requests are linked to providers/models so the system can switch between
multiple providers and track usage.

3.1 Users

3.4 EmailVerifications
------------------------------------------------------------

Purpose:
Stores email verification attempts for account activation.

The verification process is used during Sign Up and is handled through Brevo
as the project's email delivery service.

Main flow:

Sign Up
   ->
Create User
   ->
Create Verification Record
   ->
Send OTP / Verification Link through Brevo
   ->
Developer Verifies Email
   ->
Set Users.EmailVerifiedAt
   ->
Allow authenticated application access

Columns:
- VerificationId INT
  Primary Key.

- UserId INT
  Foreign Key to Users.UserId.

- CodeHash NVARCHAR(500)
  Hashed OTP verification code.

- TokenHash NVARCHAR(500) NULL
  Hashed verification token when link-based verification is used.

- Method VARCHAR(20)
  Verification method, for example:
  OTP
  Link

- ExpiresAt DATETIME2
  Expiration time of the verification request.

- Attempts INT
  Number of verification attempts.

- VerifiedAt DATETIME2 NULL
  Time the verification was successfully completed.

- CreatedAt DATETIME2
  Verification record creation time.

Relationships:
- Users 1:N EmailVerifications.

Security Rules:
- Never store the raw OTP in the database.
- Store the OTP as a secure hash.
- Never expose email provider credentials to the frontend.
- Expired verification records must not be accepted.
- Previous verification codes/tokens should be invalidated when a new
  verification request is issued.
- Resend attempts should be protected by cooldown/rate limiting.

Email Provider:
- Brevo

Brevo is an external service and does not require a dedicated database table
in the current Core ERD. The database stores verification state; Brevo is
responsible for email delivery.

8. CORE BUSINESS DATA FLOW
============================================================

1. Developer registers an account.
2. The system creates an email verification record and sends an OTP/verification link through Brevo.
3. After successful verification, the system sets Users.EmailVerifiedAt and allows authenticated access.
4. Developer creates a Problem.
5. Problem can receive multiple ProblemRequests.
6. Each request can include attachments, errors, stack traces and context.
7. The system searches for similar historical problems.
8. Similarity results are stored.
9. The AI Gateway sends optimized context to an available model.
10. Each debugging attempt is stored.
11. Developer gives feedback:
   - Solved
   - Still Have a Problem
12. If unsolved, another request/attempt is stored and the debugging loop
   continues.
13. When solved, the successful solution is stored in ProblemSolutions.
14. The system generates or updates KnowledgeArticles.
15. Article history is stored in ArticleVersions.
16. A Challenge can be generated from the problem.
17. A developer can start a ChallengeAttempt.
18. A GitHub repository can be associated with the attempt.
19. The submitted implementation can receive a ChallengeEvaluation.
20. Similar future requests can reuse successful solutions.
21. Multiple successful solution variants can later be synthesized into
    improved reusable knowledge.

9. TOKEN OPTIMIZATION DATA MODEL
============================================================

The token-saving workflow is primarily supported by:

ProblemRequests
    ->
ProblemEmbeddings
    ->
SimilarityMatches
    ->
ProblemSolutions
    ->
AIRequests

Recommended logical flow:

NEW REQUEST
    |
    v
Create ProblemRequest
    |
    v
Generate / retrieve embedding
    |
    v
Search SimilarityMatches
    |
    +---- Suitable match found
    |          |
    |          v
    |    Retrieve successful
    |    ProblemSolutions
    |          |
    |          v
    |    Send optimized context
    |    to AI Gateway
    |
    +---- No suitable match
               |
               v
         New AI debugging

Every successful new adaptation should be stored so it can be reused in
future requests.

10. ARTICLE EVOLUTION DATA MODEL
============================================================

A problem may accumulate multiple successful solutions.

Example:

Problem X
 |
 +-- Solution A -> Success
 +-- Solution B -> Success
 +-- Solution C -> Success
          |
          v
   AI Synthesis / Improvement
          |
          v
KnowledgeArticle
 |
 +-- Version 1
 +-- Version 2
 +-- Version 3

The previous article versions are preserved.

The current article points to the current version through CurrentVersionId.

============================================================
13. IMPORTANT CONSTRAINTS
============================================================

13.1 Security
- GitHub access credentials must be protected.
- LLM provider keys must never be exposed to the frontend.
- Sensitive repository information must not be exposed publicly.
- The database should not store unnecessary secrets.

13.2 Privacy
- Private repository information must remain restricted.
- Problem data should be handled according to project privacy rules.
- Sensitive credentials should not be placed in AI prompts.

13.3 History
- Previous debugging attempts must not be deleted merely because a later
  attempt succeeds.
- Previous article versions should be preserved.

13.4 Knowledge Quality
- Successful usage is evidence, but popularity alone must not be treated as
  proof of correctness.
- Knowledge improvement should consider successful outcomes and review.

============================================================
15. TRANSACTIONAL AREAS
============================================================

Operations that update multiple related records should be handled
transactionally where appropriate.

Examples:

Problem solved:
- Update Problems.Status / SolvedAt
- Store successful ProblemSolution
- Update statistics/state
- Create or update KnowledgeArticle
- Create ArticleVersion

Challenge completion:
- Update ChallengeAttempt
- Store ChallengeEvaluation
- Update any related challenge state

AI operation:
- Store AIRequest metadata/result
- Update usage tracking
- Update provider/model availability when required

16. CORE TABLES VS OPTIONAL SUPPORTING TABLES

Included in the Core ERD:
- 26 tables documented in this file.

- Notifications

============================================================
18. RECENT APPROVED CHANGES
============================================================

The database documentation was updated to reflect the latest approved
project decisions:

1. Email verification is now part of the official authentication workflow.
2. Brevo is the selected email delivery service.
3. Users now store EmailVerifiedAt.
4. EmailVerifications was added as a Core ERD table.
5. OTPs/tokens are represented as hashes, not raw values.
6. GitHub access tokens are represented as encrypted storage.
7. The Core ERD now contains 26 tables.
8. The database implementation order was updated accordingly.

The email provider itself remains an external integration and is intentionally
not modeled as a database table.

============================================================
19. FINAL DATABASE PURPOSE
============================================================

The database is not only a storage layer for chat messages.

It is designed to preserve the complete lifecycle of a real developer problem:

REAL PROBLEM
    ->
REQUEST
    ->
DEBUGGING ATTEMPTS
    ->
DEVELOPER FEEDBACK
    ->
SUCCESSFUL SOLUTION
    ->
KNOWLEDGE ARTICLE
    ->
ARTICLE VERSION HISTORY
    ->
PRACTICE CHALLENGE
    ->
GITHUB IMPLEMENTATION
    ->
AI EVALUATION
    ->
NEW SUCCESSFUL DATA
    ->
BETTER FUTURE SOLUTIONS

The central database goal is therefore:

"Store real developer problems and proven solutions in a reusable structure
that can improve future debugging, educational content, practical challenges,
and AI efficiency."
