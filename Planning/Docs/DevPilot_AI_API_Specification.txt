DEVPILOT AI
API SPECIFICATION
============================================================

Version: 1.0
Backend: ASP.NET Core Web API
Database: SQL Server
Backend Hosting: MonsterASP
Frontend: Undefined Yet
Frontend Hosting: Cloudflare Pages
Email Provider: Brevo

PURPOSE
Define the REST API contract for the approved DevPilot AI business flow:
Authentication, Email Verification, Problems, AI Debugging, Knowledge Base,
Similarity Search, Challenges, GitHub, Code Review, Telegram, AI Gateway,
and Administration.

============================================================
1. GENERAL RULES
============================================================

 /api

 JSON over HTTPS

2. AUTHENTICATION & EMAIL VERIFICATION
============================================================

POST /api/auth/register
Access: Public
Purpose: Create developer account and start email verification.

Request:
{
  "name": "Mahmoud",
  "email": "developer@example.com",
  "password": "StrongPassword",
  "turnstileToken": "..."
}

Process:
1. Validate input.
2. Create User with EmailVerifiedAt = NULL.
3. Create EmailVerification record.
4. Generate OTP or verification token.
5. Send verification email through Brevo.
6. Return verification-required result.

POST /api/auth/verify-email
Access: Public
Purpose: Verify OTP or verification token.

OTP request:
{
  "email": "developer@example.com",
  "code": "483921"
}

Link request:
{
  "token": "verification-token"
}

On success:
- Mark EmailVerifications.VerifiedAt.
- Set Users.EmailVerifiedAt.
- Invalidate active verification.
- Allow authenticated access.

POST /api/auth/resend-verification
Access: Public
Purpose: Invalidate active verification and send a new OTP/link through Brevo.

POST /api/auth/login
Access: Public
Purpose: Authenticate verified developer.

POST /api/auth/refresh
Access: Refresh token

POST /api/auth/logout
Access: Authenticated

POST /api/auth/forgot-password
Access: Public
Purpose: Send password reset email through Brevo without revealing account
existence.

POST /api/auth/reset-password
Access: Public with valid reset token.

Security:
- Store OTP/token hashes, not raw OTP values.
- Apply expiration.
- Apply maximum attempts.
- Apply resend cooldown/rate limiting.
- Never expose Brevo credentials to frontend.

4. PROBLEMS & DEBUGGING
============================================================

POST /api/problems
Access: Developer
Purpose: Create a new technical problem.

Request:
{
  "title": "JWT returns 401",
  "description": "...",
  "errorMessage": "401 Unauthorized",
  "stackTrace": "...",
  "technologyHint": "ASP.NET Core"
}

POST /api/problems/{problemId}/requests
Access: Developer
Purpose: Add another request/input when the problem is still unresolved.

POST /api/problems/{problemId}/debug
Access: Developer
Purpose: Run AI debugging.

Processing:
1. Validate input.
2. Normalize technical context.
3. Search similar historical problems.
4. Evaluate similarity.
5. Retrieve successful reusable solutions when appropriate.
6. Build optimized AI context.
7. Call AI Gateway.
8. Select available provider/model.
9. Validate/normalize response.
10. Store AI request/response.
11. Store DebuggingAttempt.
12. Return solution.

Response example:
{
  "success": true,
  "data": {
    "attemptId": 12,
    "attemptNumber": 1,
    "rootCause": "...",
    "solution": "...",
    "whyItWorks": "...",
    "similarProblems": [
      {
        "problemCode": "DEV-000102",
        "similarityScore": 0.94
      }
    ]
  }
}

POST /api/problems/{problemId}/attempts/{attemptId}/feedback
Access: Problem owner
Request:
{
  "result": "Solved",
  "comment": "..."
}

Allowed:
- Solved
- StillHaveAProblem

Solved:
- Mark problem solved.
- Store successful solution.
- Update knowledge/article workflow.

StillHaveAProblem:
- Store feedback.
- Start another debugging attempt.

GET /api/problems/{problemCode}
Access: Owner or public article/knowledge view according to visibility rules.

GET /api/problems/{problemId}/history
Access: Owner
Returns requests, attempts, feedback, and successful solutions.

11. AI GATEWAY
============================================================

These endpoints are internal and should not be publicly exposed.

POST /api/ai/generate
Purpose:
Central AI operation entry point.

Request:
{
  "operationType": "Debugging",
  "problemId": 1001,
  "context": "..."
}

The AI Gateway handles:
- Provider selection
- Model selection
- Usage tracking
- Retry
- Failover
- Response normalization
- Prompt version selection

Provider behavior:
1. Select highest-priority available provider/model.
2. Call provider.
3. On success, store usage.
4. On rate limit/error, mark provider/model temporarily unavailable.
5. Retry with next available provider.
6. Do not expose internal switching to user.

GET /api/admin/ai/providers/health
Access: Administrator

GET /api/admin/ai/providers
Access: Administrator

15. SECURITY REQUIREMENTS
============================================================

- HTTPS only.
- Secure authentication and authorization.
- Validate all request data.
- Rate limit abuse-sensitive endpoints.
- Use Cloudflare Turnstile where appropriate.
- Never expose AI provider API keys to frontend.
- Never expose GitHub tokens to frontend.
- Store GitHub credentials securely/encrypted.
- Store OTP/token as hashes.
- Expire verification/reset records.
- Apply resend cooldown.
- Validate GitHub webhook authenticity.
- Use least-privilege GitHub permissions.
- Keep private repository data private.
- Do not place sensitive credentials inside AI prompts.
- Centralized exception handling.
- Never return internal stack traces in production.

============================================================
16. TOKEN OPTIMIZATION RULES
============================================================

New request
 ->
Normalize
 ->
Similarity Search
 ->
Suitable solution?
    |
    +-- YES -> retrieve successful solution -> adapt with AI
    |
    +-- NO  -> fresh AI debugging

The system must:
- Search knowledge before fresh AI calls.
- Reuse successful solutions.
- Send only relevant repository files.
- Cache reusable output where appropriate.
- Track token/request usage.
- Save successful adaptations.
- Use multiple providers with failover.

============================================================
17. ARTICLE EVOLUTION RULES
============================================================

When multiple successful solutions exist:

1. Collect successful variants.
2. Analyze supporting evidence.
3. Synthesize improved solution.
4. Generate new ArticleVersion.
5. Preserve previous versions.
6. Update CurrentVersionId.

The newest version should represent the best currently supported solution,
not simply the most recently generated text.
